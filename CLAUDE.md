# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FB Group AutoPost: a Chrome extension that posts to Facebook groups while imitating a human, plus .NET servers that let people edit configs and control the extension remotely. The repo holds three parts:

- `src/` + `tests/` + `SIRIAUTOPOST.sln`: the **new** Clean Architecture solution (.NET 10, EF Core, PostgreSQL). It is the API behind the Angular dashboard (JWT auth, workspaces, social accounts, post scheduling, error reports, media library, anti-ban/offline settings) and the job API the extension's cloud mode posts from (device pairing, `/api/device/*`). New backend work goes here.
- `backend/SIRI.AUTOPOST.Server/`: the **legacy** server, a single-project minimal API that the extension and the legacy web UI talk to today.
- `client/`: the Chrome extension (Manifest V3, plain ES modules, no build step). Since 2.2 it is a **client**: it posts and reports, and its only page is `status.html` (status + the approval step of pairing). Every setting, button, pairing and device control lives in the Angular app on `SIRIAUTOPOST.Api`.

User-facing strings (UI text, API error messages, log messages) are in **Thai**. Code comments are in English. Keep both conventions.

The sibling repo `siri_autopost_ui` holds the new Angular frontend (the AutoPost Dashboard design, talking to `SIRIAUTOPOST.Api`) at its root, and a Vite-hosted copy of the legacy web UI in `legacy/`. See "Duplicated files" below.

## New solution (`SIRIAUTOPOST.sln`)

```bash
dotnet build SIRIAUTOPOST.sln
dotnet test SIRIAUTOPOST.sln                     # integration tests need PostgreSQL, see below
dotnet test tests/SIRIAUTOPOST.Domain.Tests      # one project
dotnet test SIRIAUTOPOST.sln --filter "FullyQualifiedName~PostTests"   # one class/test

# API on http://localhost:5100 (OpenAPI at /openapi/v1.json in Development)
cd src/SIRIAUTOPOST.Api && dotnet run

# Migrations live in Infrastructure; the Api is the startup project
dotnet ef migrations add <Name> -p src/SIRIAUTOPOST.Infrastructure -s src/SIRIAUTOPOST.Api -o Data/Migrations
```

- Dev connection string is in `src/SIRIAUTOPOST.Api/appsettings.Development.json` (`localhost:5432`, database `siriautopost`). `Database:MigrateOnStartup` is true only in Development.
- Auth is JWT bearer (`Infrastructure/Auth`, `Jwt` config section). `Jwt:Key` must be at least 32 characters or startup fails; only Development ships one. A fallback policy requires a signed-in user everywhere, so anonymous endpoints need `[AllowAnonymous]`. Handlers get the caller from `ICurrentUser` (the `sub` claim) and check access with `WorkspaceAccess.RequireAsync(ws, user, minRole)` (see "Workspace roles"), which answers 404 for a workspace the caller has no part in.
- Google sign-in: `GET /api/auth/config` returns `googleClientId` (from `Google:ClientId`, env `Google__ClientId`; empty = button hidden). The web app sends the Google Identity Services ID token to `POST /api/auth/google`; `GoogleTokenVerifier` checks it via Google's tokeninfo endpoint (audience, issuer, `email_verified`). A known email signs in (blocked users get 403), an unknown one creates a shop user + workspace with no password hash. Create an OAuth Web client in Google Cloud and add the site origin (e.g. `http://localhost:4200`) to its authorized JavaScript origins.
- Startup (`PrepareDatabaseAsync`) migrates when configured, then `AdminAccountSeeder` creates the platform admin from `Admin:Email`/`Admin:Password` (Development: `admin@autopost.local` / `admin1234`).
- Every new workspace is filled by `DemoWorkspaceSeeder` (`IWorkspaceSeeder`): the design's 7 social accounts (the Facebook page has 20 groups), 4 snippets, a week of post history, a week of queued posts and 5 open error reports. These sample accounts have no device (`AccountDto.connected` false), so their posts are never handed out and stay queued. Integration tests must not assume an empty workspace.
- Devices (`Features/Devices`). The owner creates a pairing code (`DevicePairing`, 10 minutes, single use, day-old codes are deleted whenever a new one is made; the number of devices comes from the owner's plan, `PlanSetting.Devices`: free/basic 1, pro 3, agency unlimited by default). The extension trades it at `POST /api/device/pair` for a device key (only its SHA-256 is stored) and the workspace gets a connected Facebook account (`SocialAccount.DeviceId`). Device endpoints authenticate with the `X-Device-Key` header (`DeviceKeyAuthenticationHandler`, scheme `DeviceKey`, open CORS policy `Devices`) and read the caller from `ICurrentDevice`. The web app controls a device with `PUT /api/workspaces/{ws}/devices/{id}` (`UpdateDeviceCommand`, admin role): `name` (its account follows: `SocialAccount.FollowDevice`) and `jobsPaused` (`Device.JobsPaused`: `ClaimJobCommandHandler` hands out nothing, the heartbeat reports it); null keeps a value. Unbinding (the owner's `DELETE` and the admin's) goes through `DeviceRevocation`: it fails the device's claimed and still-open posts, so nothing stays `Posting` or queued for a browser that is gone. The heartbeat's `jobsPaused` is true when the device is paused **or** the owner cannot post (`!CanPost`), so the extension stops asking.
- Jobs. The extension sends `PUT /api/device/groups` (name + URL; they become the account's `Groups`/`GroupLinks`, names unique) and polls `POST /api/device/jobs/claim`. `ClaimJobCommandHandler` hands out one due post at a time per device, keeps the anti-ban minimum gap per account, fails posts over the platform's 24-hour limit (`quota`) or for a group the extension no longer has, skips posts later than `OfflineSettings.MaxLateness`, and fails claims not reported within 15 minutes (never retried automatically: they may have gone out). `POST /api/device/jobs/{id}/result` completes it (`needsLogin` → `session` + account `relogin`, `blocked` → `rate_limit`). Claiming writes a `post` event. `OfflineSettings.MaxLateness` counts from the later of the due time and the end of the anti-ban gap, so a post held back by pacing is not "late" (two posts due together would otherwise leave the second one skipped). `PUT /api/device/groups` accepts up to `MaxGroups` (5,000) groups, a repeated name is dropped (the extension makes names unique itself and keeps the name the web already has for an address, because queued posts name their group), and it writes `device.groups` only when the list changed. Connected accounts without groups cannot be scheduled for.
- Extension campaigns (`Features/Extension`, `ExtensionController` for the web app, the rest of `DeviceApiController` for the device). The extension's own settings page lives on in the web app's "ชุดโพสต์" screen: `ExtensionConfig` holds one device's settings JSON (the `client/lib/shared.js` shape, stored as `text` so identical saves keep the `Revision`; `HasContent` is worked out on save), `ExtensionImage` its media per workspace under the extension's own ids (never overwritten; unused ones older than 1 hour are deleted after each save that changed something), `DeviceState` the last reported `state`, `DeviceLog` the log (1,000 lines kept per device) and `DeviceCommand` the buttons pressed on the web (pending → sent → done, expired after 10 minutes, names in `DeviceCommand.Allowed` = `remoteCommands` in `background.js`). Saves are optimistic: `baseRevision` must match or 409, `null` overwrites. The device calls `POST /api/device/sync` every 30 s (state, new log lines, `takeCommands`) and gets the revision, `hasContent` and its commands; `GET/PUT /api/device/config`, `POST /api/device/images/missing`, `GET/PUT /api/device/images/{id}` (`{ name, type, data: data URL }`) and `POST /api/device/commands/{id}/result` do the rest. `Common/ExtensionSettings` reads the JSON on the server and mirrors `campaignImageIds`/`hasContent` of the extension (like `Services/Helpers.cs` of the legacy server): keep them in step. Web commands are never lost: `DeviceCommand` is open while pending or sent, `TakeAsync` hands out pending commands **and** sent ones that have no result yet (`again: true`, so a held sync whose answer the extension threw away delivers it again), `Stale` expires both after 10 minutes, and the extension keeps a `cmdLedger` of ids it already ran so a redelivered command is acknowledged, not run twice. `Send` raises a `sent` `device.command` event; `StartsPosting(cmd)` commands (start, runNow, testPost) are refused for blocked owners. The Telegram bot token is private: a viewer or editor gets it redacted from `GET .../config` (`ExtensionSettings.BotToken`), and a save from a role below admin keeps the stored token (`WithBotToken`). The reported `state` is cut to `MaxStateChars` (300,000) and logs to 1,000 lines so one huge device cannot make `sync` fail.
- Device events (`Domain/Entities/DeviceEvent.cs`, table `DEVICE_EVENTS`, `Features/Events`, `EventsController`). Everything a device does is also written as a `DeviceEvent` row (`Seq` = identity, types in `DeviceEventType`: `device.paired/revoked/online/state/log/log_cleared/command/config/groups/updated`, `post`) in the same `SaveChanges` as the change, by the handlers through `IDeviceEventRepository.Add` (`Common/DeviceEvents.Make` builds the payload in the API's JSON conventions). `AppDbContext.SaveChangesAsync` publishes the saved rows to `IDeviceEventBus` (`Infrastructure/Services/DeviceEventBus`, in-process channels; swap for Redis pub/sub when the API runs on more than one instance). The web app streams them: `GET /api/workspaces/{ws}/events/stream` is Server-Sent Events (`id` = Seq, `event` = type, `data` = `DeviceEventDto`; a `retry: 3000` + `event: ready` (`{head}`) first, a `: ping` every 15 s, `event: reconnect` after 30 minutes, on shutdown or when the backlog is too big), `?after=<seq>` / `Last-Event-ID` first replays what the client missed from the database, and `GET /api/workspaces/{ws}/events?after=&take=` is the same backlog as JSON (`DeviceEventsPageDto`). Events are pruned to 2,000 per device on the device's sync. The device side long-polls: `POST /api/device/sync` with `wait: true` and `takeCommands` holds the call up to 25 s (`DeviceSyncCommandHandler.MaxWait`) until a `device.command` event wakes it, so a button on the web reaches the extension within a second. New device-side state that the web should see at once needs an event; a new event type goes in `DeviceEventType.All`. The admin health has the live counts (`EventStreams`, `DeviceWaits`, `EventsPublished`, `EventsDropped`), and `UseApi` stops the bus on `ApplicationStopping` so streams and waits end at once on deploy.
- Extension download. `GET /api/extension/download` (anonymous, `ExtensionDownloadController`) zips the runtime files of `client/` (manifest, background/content/status, `icons/`, `lib/`; never `config/` or `tools/`) under `autopost-extension/`, cached until a file changes. It finds the folder in `Extension:Path`, `./extension` next to the app (the Api Dockerfile copies it there: add a new runtime file to that `COPY` list and to `RootFiles`), or `client/` above the content root. The web app links it from the add-device dialog and from `/connect-extension` when no extension answers.
- Presence. A device is online when it called in within 100 s. `EngineSettingsDto.extensionOnline` is false while the offline simulation is on, or when devices are paired and none is online (`simulatedOffline`, `devices`, `devicesOnline` tell the cases apart). Reconnecting after the simulation puts held posts back in the queue.
- Workspace roles (`WorkspaceRole`: viewer < editor < admin < owner). The owner is `Workspace.OwnerId`; everyone else is a `WorkspaceMember` (invited by email, `UserId` set on signup or straight away when the account exists). Handlers check access with `WorkspaceAccess.RequireAsync(ws, user, minRole)`: viewer reads, editor posts/library/reconnect/skip waiting, admin engine settings, simulation, devices and members. Too low a role is a `ForbiddenException` (403); no access at all stays 404.
- Plans and billing (`Domain/Entities/Billing.cs`, `Application/Features/Billing`, `Infrastructure/Payments`). `PlanSetting` rows (seeded with `HasData`, edited by the platform admin) hold price and limits (accounts, posts/day, devices, seats; null = unlimited). `PlanLimits.ForAsync(owner)` applies the owner's `LimitOverrides` (`EffectiveLimits`, 0 = unlimited); limits always come from the workspace owner's plan (`WorkspaceDto.Limits`, `BillingDto.Limits/Usage`).
- Payments go through **Stripe** (`Stripe.net` 53). `IPaymentGateway` (`Application/Interfaces/Payments.cs`) is implemented by `StripePaymentGateway`; the `Stripe` section is `StripeOptions` (env `Stripe__SecretKey`, `Stripe__WebhookSecret`, `Stripe__ReturnBaseUrl`, `Stripe__Currency` = `thb`, `Stripe__PortalConfigurationId`). An empty secret key means `Enabled` is false: `BillingDto.PaymentsEnabled` is false, `PaymentsConnected` of the health is false and a paid plan answers 422 (`ChangePlanCommandHandler.NotReady`). `ReturnBaseUrl` empty = the browser's `Origin` (`Auth/AppUrls`). Prices are whole baht (`Money` converts to satang). `PUT /api/billing/plan` (`ChangePlanCommand` → `PlanChangeDto`): Free → paid creates a Checkout Session (subscription mode, inline `price_data` on a Stripe product `autopost_<plan>` made on first use, a promo code = once-only amount-off coupon from `Pricing.FirstDiscount`, yearly = 20% off) and answers `CheckoutUrl`; with a subscription the item is changed with `always_invoice` + `error_if_incomplete` (a declined card leaves the plan as it was), Free = `cancel_at_period_end`, choosing the current plan again takes the cancellation back. **The plan only changes from what Stripe says**: `POST /api/webhooks/stripe` (`StripeWebhookController`; `StripeWebhookParser` checks `Stripe-Signature`, an invalid one is 400; events `checkout.session.completed`, `customer.subscription.created/updated/deleted`, `invoice.paid`, `invoice.payment_failed`, `refund.created/updated`) and `POST /api/billing/checkout/confirm` (the customer's return from Checkout) both end in `PaymentSync`, which re-reads the subscription from Stripe (so events arriving out of order cannot move the plan back in time) and dedupes through `PAYMENT_EVENTS` (keys `evt_…` and `checkout:{session}`; the unique key throws `DuplicateKeyException`, which the handler treats as done). `User` carries `StripeCustomerId`, `StripeSubscriptionId`, `PlanRenewsAt`, `CancelAtPeriodEnd` (`ApplySubscription`, `MarkPastDue`, `MarkPaid`, `EndSubscription`, `DowngradeToFree`); `Transaction` carries the invoice, payment intent, refund and receipt ids. `POST /api/billing/portal` opens Stripe's billing portal (card, invoices). Admin: refunds go to Stripe (`Transaction.RefundOf`), `RetryPaymentCommand` pays an open invoice again, suspending or banning calls `SetBillingPausedAsync` (`pause_collection`) before saving so nobody is billed while blocked, and `User.SetPlanByAdmin` is refused while the customer has a subscription (the plan then follows Stripe). Signing up with a plan no longer grants it (the user starts Free and the web app sends them to Checkout); `Trial` only remains on rows from before Stripe. Tests: the integration tests use `FakePaymentGateway` (with the real `StripeWebhookParser`) and signed sample events from `StripeEvents`; `StripePaymentGatewayTests` pins the HTTP calls with a stubbed `HttpClient`. **Nothing here has been run against live Stripe**: try a test key and `stripe listen --forward-to localhost:5100/api/webhooks/stripe` first.
- Customer status (`User.Status`: active, trial, past_due, suspended, banned; `Paused`). Suspended and banned users are blocked: login answers 403 with `LogInCommandHandler.BlockedMessage`, and the JWT `OnTokenValidated` hook rejects their existing tokens. `CanPost` is false for blocked or paused owners, so `ClaimJobCommandHandler` hands out nothing; it also enforces the plan's posts/day on connected accounts only. `past_due` is set by `invoice.payment_failed` and cleared by `invoice.paid`; the admin's status change keeps `Paused` in step (suspending pauses posting, restoring resumes it).
- Platform admin API (`Features/Admin/Admin.cs`, `AdminController`, `[Authorize(Roles = "admin")]`): summary (subscriptions + 12 months of net revenue on the Bangkok calendar), customers, jobs, status/pause/plan/limits/note, device revoke, retry failed, transactions (refund once, record payment), plan settings, promo codes, `health` and `audit`. Counts of "real" posts only include accounts that have a device, so the sample data never shows up there.
- Activity log (`AuditEntry`, table `AUDIT_ENTRIES`, no foreign keys). Every admin command writes one through `AdminAudit.Record` before saving (`From`/`To` are values such as plan keys or `accounts=5 posts=-`, not display text); self-service plan changes in `ChangePlanCommandHandler` write `PlanChanged` too. That plan history is what `PlatformMetrics` (Domain) rebuilds past plans from: MRR now vs 30 days ago and churn per 30-day window. A new admin command needs its audit line.
- Assist mode. `POST /api/admin/customers/{id}/impersonate` returns a one-hour token for the customer carrying the admin in the `act` claim (`JwtTokenService.ActorClaim`, `ICurrentUser.ImpersonatorId`). `ReadOnlyImpersonationMiddleware` refuses every non-GET request for such a token (403), `/api/auth/me` does not mark the customer as seen, and the JWT hook lets it through for suspended customers as long as the actor is still an admin.
- Health (`GET /api/admin/health`, `GetPlatformHealthQuery`): MRR, churn, devices active in 24 h, 7-day success rate, API p95 from `RequestTimingMiddleware` (last 1,000 `/api` requests, in memory), a database ping (`IDatabaseProbe`), the due queue, the extension version that `GET /api/extension/download` serves (read from the manifest through `IExtensionPackage`) and the 24 h error rate. `PaymentsConnected` is true when `Stripe:SecretKey` is set. Held syncs and the event stream are left out of the p95 (`RequestTimings`).
- Docker: `src/SIRIAUTOPOST.Api/Dockerfile` (build context = repo root) and `docker-compose.saas.yml` (db + api + web, where web builds `siri_autopost_ui` from `UI_PATH`, default `../siri_autopost_ui`, and its nginx proxies `/api` to `api:8080`). The connection string sets `Gss Encryption Mode=Disable` because the aspnet image has no GSSAPI library. The `https` profile adds Caddy (`caddy reverse-proxy --from $DOMAIN --to web:80`) for automatic certificates; `DOMAIN=localhost` uses Caddy's local CA. The Stripe values pass through as `Stripe__*` (empty = payments off). Kubernetes and Jenkins live in `deploy/` (`deploy/README.md`: required env keys, the Stripe webhook, limits that must agree: nginx `client_max_body_size` 300m for uploads, API memory 2Gi).
- CI (`.github/workflows/ci.yml`, PostgreSQL 18 like the compose files): the solution built with `-warnaserror` and tested against a PostgreSQL service, the legacy server built **and started** on a fresh database with `test-online.mjs` run against it, `node --check` on the extension plus `test-cloud.mjs` against a freshly started API (Development admin), and the API Docker image.
- Tests that need time to pass use `ApiFactory.Clock.Advance(...)` (dispose it to move the clock back).
- `SIRIAUTOPOST.Api.IntegrationTests` runs the real API through `WebApplicationFactory<Program>` against PostgreSQL. It drops and recreates the database `siriautopost_test` (override the whole connection string with `SIRIAUTOPOST_TEST_DB`).
- Layer rules. **Domain** references nothing. **Application** references Domain only. **Infrastructure** references Application and Domain. **Api** references Application and Infrastructure. Keep entity invariants in Domain (`Post.Schedule`/`Retry`/`DismissError`, `Workspace.UpdateAntiBan`, `AntiBanSettings.Validate`, `MediaFile.Create`) and input-shape checks in FluentValidation validators (`Application/Validators/Validators.cs`).
- CQRS without a mediator library. Each command or query is a record plus a handler, grouped per feature in `Application/Features/<Feature>/<Feature>.cs`, and it has to be registered in `Application/DependencyInjection.cs`. `AddCommand<,,>` wraps each handler in `ValidationCommandHandlerDecorator`, so validators always run first. Controllers inject `ICommandHandler<,>`/`IQueryHandler<,>` with `[FromServices]`.
- Errors. `ExceptionHandlingMiddleware` maps `ValidationException` to 400 (`ValidationProblemDetails` with camelCase keys), `AuthenticationException` to 401, `ForbiddenException` to 403, `NotFoundException` to 404, `ConflictException` to 409 and `DomainException` to 422. Anything else becomes a 500.
- JSON: enums are snake_case strings (`fb`, `pending_approval`) and numbers are strict JSON numbers, set for both MVC and `ConfigureHttpJsonOptions` so the OpenAPI document (and the UI's generated types) match. The client sends `startAt` with its local UTC offset so weekday repeats follow the user's calendar.
- EF Core: one `IEntityTypeConfiguration` per entity in `Infrastructure/Data/Configurations/Configurations.cs`, uppercase table names (SCREAMING_SNAKE_CASE: `USERS`, `WORKSPACES`, `POSTS`...), snake_case column naming, enums stored as strings, and `AppDbContext` doubles as `IUnitOfWork`. Workspace anti-ban/offline settings are owned JSON (`jsonb`) columns. Store `DateTimeOffset` values as UTC, because Npgsql rejects non-zero offsets for `timestamptz`.
- When the API contract changes, refresh `openapi.snapshot.json` in `siri_autopost_ui` (`curl localhost:5100/openapi/v1.json`) and run `npm run gen:api` there.

## Legacy backend configuration quirks

- `Program.cs` reads a `.env` file from the current directory or its parent before startup. Variables already set in the environment win.
- Connection string: `ConnectionStrings:Default`, falling back to `AppSettings:ConnectionStrings`. Its database name is then **replaced** by `Database:Name`: `SIRIAUTOPOST` in Development and `SIRIAUTOPOST_PRD` otherwise, Docker included. The server creates the database on first start, so the DB user needs CREATEDB.
- The database is shared with other apps. Every table is prefixed `FBAP_` and upper case (`FBAP_PROFILES`, migration `UppercaseTableNames`; raw SQL quotes the names), the migrations history table is `fbap_ef_migrations` (lower case on purpose: renaming it would re-run `Initial` on existing databases), and columns are snake_case (`UseSnakeCaseNamingConvention`). Changing a table name needs a migration **and** the quoted SQL in `ProfileStore`, `AdminEndpoints` and `DeviceEndpoints`; CI starts the server, so a mismatch fails there.
- The first start seeds an admin from `Admin:Username`/`Admin:Password`. If no password is set, it generates one and logs it.
- Use the **root** `docker-compose.yml` (the old `backend/docker-compose.yml` is gone).
- The `<None Include="..\..\dashboard.html" ...>` items in the csproj resolve to the repo root, not `client/`, so a plain `dotnet publish` doesn't copy the extension files. The Dockerfile copies them into `/out/extension` itself.

## Legacy architecture

### Three API surfaces (`backend/SIRI.AUTOPOST.Server/Endpoints/`)

- `AuthEndpoints`: `/api/auth/*`, cookie auth (`fbap.auth`). Unauthenticated `/api` calls get a 401; page requests are redirected to `/login.html`.
- `AdminEndpoints`: `/api/*` (requires login). Covers profiles (configs), profile images, devices, live device state and logs, and remote commands.
- `DeviceEndpoints`: `/api/device/*`, used by the extension's service worker. It authenticates with the `X-Device-Key` header (only its SHA-256 hash is stored) and has an open CORS policy. `POST /heartbeat` uploads state and logs, and returns the config revision and any pending commands.

### Domain model (`Data/AppDb.cs`)

- **Profile**: one extension "settings" JSON blob (version 2 shape: `campaigns`, groups, posts, global settings, Telegram), stored as `jsonb`, with a `Revision` counter. Several devices can share one profile.
- **ProfileImage**: media stored as bytes, keyed `(ProfileId, ImageId)`. The ID matches the extension's `img:<id>` storage key. An image ID never changes content, so existing IDs are never overwritten.
- **Device**: one computer running the extension, with its last reported `State` (jsonb). It counts as online if seen within the last 100s (`AdminEndpoints.OnlineWindow`).
- **DeviceCommand**: a queued remote command (pending → sent → done/expired). Commands older than 10 minutes expire instead of running late.

### Settings sync (`Services/ProfileStore.cs` + `client/background.js` "online" section)

- `SaveSettings` uses optimistic concurrency. The caller sends `baseRevision`; if the row has moved on, the API returns 409, and `null` overwrites. Saving identical JSON keeps the revision so devices don't reload for nothing.
- After each save, images that no settings reference and that are older than 1 hour are deleted. The grace period exists because editors upload images before saving the settings that use them.
- The extension syncs every 30s through a `chrome.alarms` entry (`fbap-sync`). It pulls when the revision changes, fetches only missing images, and pushes local edits after about 4s. When both sides changed, the server wins.
- `Services/Helpers.cs` `SettingsJson` reads the extension's JSON on the server side. It mirrors `migrateSettings`/`campaignImageIds` in `client/lib/shared.js` and `hasContent` in `client/lib/backup.js`. If the settings shape changes, update both sides.

### The web editor reuses the extension's dashboard

The server serves `client/dashboard.{html,css,js}`, `lib/*.js` and `icons/` under `/app/`, located at runtime by `ExtensionPath()`. `GET /app/dashboard.html` injects `wwwroot/web/shim.js` before `dashboard.js`. The shim replaces `chrome.storage.local`, `chrome.runtime.sendMessage` and `chrome.permissions` with REST calls:

- `settings` and `img:*` storage keys map to profile endpoints (`?profile=<id>`).
- `sendMessage` commands become `DeviceCommand`s for the selected device (`?device=<id>`). The shim polls until the command is done.

So `dashboard.js` must keep talking only through those chrome APIs. A new chrome API used there needs a shim implementation too. `wwwroot/index.html` + `web/admin.js` hold the profile and device management page.

### Extension internals (`client/`)

- `background.js` (service worker): every campaign has its own `chrome.alarms` entry (`fbap:<campaignId>`). Ticks are serialized through one promise chain, so only one post happens at a time across all campaigns, in a dedicated worker window. It also handles anti-block rules (daily quotas, group cooldowns, auto-pause on Facebook warnings), Telegram notifications, the bundled-config loader, and server sync.
- `content.js` is injected with `chrome.scripting.executeScript` into the Facebook tab. It does the DOM steps (scroll, type, attach, click post).
- Messaging is `{ target: 'fbap-bg' | 'fbap-content', cmd, ...args }` → `{ ok, ... }`. The dashboard calls background commands, and background calls content handlers.
- Remote commands: the names in `AdminEndpoints.AllowedCommands` must match `remoteCommands` in `background.js`, and the shim's `LOCAL_ONLY` list blocks commands the web can't run.
- `lib/shared.js` holds settings defaults, `migrateSettings`, spintax and the text composer. `lib/backup.js` handles import/export and the bundled `config/autopost-config.json`, which loads automatically only when the browser profile has no data. `lib/siri-import.js` + `lib/zip.js` import SIRI exports.
- The files under `client/config/` (`extra-groups.txt`, `drop-images.txt`, `image-fixes/`) are only inputs for `tools/siri-to-config.mjs`. The extension never reads them at runtime.
- Cloud mode (`background.js` "cloud" section, shown on `status.html`): pairs with `SIRIAUTOPOST.Api` (storage key `cloud`), and every 30 s (`fbap-cloud` alarm, run through `enqueue` so it never overlaps a campaign post) sends a heartbeat and the enabled groups of every campaign, claims one job and posts it with `postToGroup`. Job media is stored as `cloudimg:<id>` (content.js `loadFiles` accepts full keys) and removed after the post, so the `img:` orphan cleanups never touch it. It is independent of Start/Stop and of the legacy online mode; the shim's `LOCAL_ONLY` keeps the `cloud*` commands out of the web editor. The same alarm also runs `cloudConfigSync` **outside** `enqueue` (so a "stop" from the web arrives during a post): it reports state and log, syncs the settings with `ExtensionConfig` by the legacy rules (first sync with an empty web config uploads this browser's settings, then the changed side wins, the web wins when both changed; `cloud.configRevision`/`configHash` find local edits, `cloudPulled` makes the dashboard reload), then runs the web's commands through `runRemoteCommands`. Local edits push about 4 s after the change (`scheduleCloudPush`). Between alarms, `cloudListen()` (started by `ensureCloudAlarm` and the alarm) loops on `cloudConfigSync({ wait: true })`: the server holds `/api/device/sync` open until the web sends a command, so buttons arrive within a second; `cloudWake()` aborts the held call (`cloudApi` takes a `signal`, the answer is `{ aborted: true }`) whenever a plain sync is requested, so an edit or the alarm is never stuck behind it, and a 20 s `getPlatformInfo` tick keeps the worker alive while a call is open. `cloud.paused` mirrors the web's `jobsPaused`. A 401 from the API (unbound on the web) resets `cloud` to "not paired" (`cloudForget`); the campaigns stay. `test-cloud.mjs` covers it.
- Pairing starts on the web: "Connect this Chrome" opens `<web origin>/connect-extension#ap-pair=1&code=...&name=...&ws=...`; `chrome.tabs.onUpdated` (`connectRequest`) sends that tab to `status.html#pair=...`, where one "Allow" click requests the optional `<all_urls>` capture permission (Chrome grants it only on a click in the extension) and runs `cloudPair`. The API URL is always the origin of that page. There is no manual code entry.
- `dashboard.html/js` is retired inside the extension (it redirects to `status.html` on `chrome-extension:`); it stays only as the legacy server's web editor. The legacy online mode still runs in `background.js` for browsers already connected, but has no UI any more.

## Duplicated files

`siri_autopost_ui/legacy/` contains byte-identical copies of `client/dashboard.{css,js}`, `client/lib/*` and `client/icons/`, and near-copies of `client/dashboard.html` and `backend/SIRI.AUTOPOST.Server/wwwroot/{index,login}.html` + `web/*`. The near-copies drop the `/app/` path prefix and load the shim as a module. `siri_autopost_ui/src/app/core/ext/lib/` holds byte-identical copies of `client/lib/{shared,backup,zip,siri-import}.js` (with hand-written `.d.ts` files) for the Angular campaigns screen. When you change any of these files, mirror the change in the other repo. Library code shared with browser bundles must not import Node modules by a literal specifier (see the `node:zlib`/`node:crypto` fallbacks in `zip.js`/`siri-import.js`).

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FB Group AutoPost: a Chrome extension that posts to Facebook groups and pages while imitating a human, plus .NET servers that let people edit configs and control the extension remotely. The repo holds three parts:

- `src/` + `tests/` + `SIRIAUTOPOST.sln`: the **new** Clean Architecture solution (.NET 10, EF Core, PostgreSQL). It is the API behind the Angular dashboard (JWT auth, workspaces, social accounts, the collection → link set → schedule posting flow, error reports, media library, anti-ban/offline settings, notifications, reports) and the job API the extension's cloud mode posts from (device pairing, `/api/device/*`). New backend work goes here.
- `backend/SIRI.AUTOPOST.Server/`: the **legacy** server, a single-project minimal API that the extension and the legacy web UI talk to today.
- `client/`: the Chrome extension (Manifest V3, plain ES modules, no build step). Since 2.2 it is a **client**: it posts and reports, and its only page is `status.html` (status + the approval step of pairing). Every setting, button, pairing and device control lives in the Angular app on `SIRIAUTOPOST.Api`.

User-facing strings (UI text, API error messages, log messages) are in **Thai**. Code comments are in English. Keep both conventions.

The sibling repo `siri_autopost_ui` holds the new Angular frontend (the AutoPost Dashboard design, talking to `SIRIAUTOPOST.Api`) at its root, and a Vite-hosted copy of the legacy web UI in `legacy/`. See "Duplicated files" below.

## New solution (`SIRIAUTOPOST.sln`)

```bash
dotnet build SIRIAUTOPOST.sln
dotnet test SIRIAUTOPOST.sln                     # integration tests need PostgreSQL, see below
dotnet test tests/SIRIAUTOPOST.Domain.Tests      # one project
dotnet test SIRIAUTOPOST.sln --filter "FullyQualifiedName~PostTests"   # one class/test

# API on http://localhost:5100 (OpenAPI at /openapi/v1.json in Development)
cd src/SIRIAUTOPOST.Api && dotnet run

# Migrations live in Infrastructure; the Api is the startup project
dotnet ef migrations add <Name> -p src/SIRIAUTOPOST.Infrastructure -s src/SIRIAUTOPOST.Api -o Data/Migrations
```

- Dev connection string is in `src/SIRIAUTOPOST.Api/appsettings.Development.json` (`localhost:5432`, database `siriautopost`). `Database:MigrateOnStartup` is true only in Development.
- Auth is JWT bearer (`Infrastructure/Auth`, `Jwt` config section). `Jwt:Key` must be at least 32 characters or startup fails; only Development ships one. A fallback policy requires a signed-in user everywhere, so anonymous endpoints need `[AllowAnonymous]`. Handlers get the caller from `ICurrentUser` (the `sub` claim) and check access with `WorkspaceAccess.RequireAsync(ws, user, minRole)` (see "Workspace roles"), which answers 404 for a workspace the caller has no part in.
- Google sign-in: `GET /api/auth/config` returns `googleClientId` (from `Google:ClientId`, env `Google__ClientId`; empty = button hidden). The web app sends the Google Identity Services ID token to `POST /api/auth/google`; `GoogleTokenVerifier` checks it via Google's tokeninfo endpoint (audience, issuer, `email_verified`). A known email signs in (blocked users get 403), an unknown one creates a shop user + workspace with no password hash. Create an OAuth Web client in Google Cloud and add the site origin (e.g. `http://localhost:4200`) to its authorized JavaScript origins.
- `Program.cs` also reads `KEY=value` lines of a `.env` (current folder, then parents) into the environment before startup (variables already set win), so `dotnet run` outside Docker takes the API's own names (`Jwt__Key`, `Stripe__SecretKey`, ...). The root `.env.example` is shared with the compose files, which map `JWT_KEY`/`ADMIN_EMAIL`/`ADMIN_PASSWORD` to those names.
- Startup (`PrepareDatabaseAsync`) migrates when configured, then `AdminAccountSeeder` creates the platform admin from `Admin:Email`/`Admin:Password` (Development: `admin@autopost.local` / `admin1234`). Since 2026-10-06 an account that already exists under `Admin:Email` (a customer who signed up first) is made an admin at that start instead (`User.PromoteToAdmin`, password kept, no password needed in the config) and moved to the top plan, Agency/"Premium" (`SetPlanByAdmin`: an admin is not in the admin customer list, so the plan cannot be granted there; a plan paid through Stripe is left alone; every start re-checks it, so an admin made by a hand-run SQL `UPDATE` gets the plan at the next start; `AdminPromotionTests`): this is how to promote a live user without touching the database, set `Admin__Email` to their address and redeploy; they sign in again to get a token with the role.
- A new workspace starts EMPTY (2026-10-06): `DemoWorkspaceSeeder` (`IWorkspaceSeeder`) is a no-op now. It used to add the design's 7 sample accounts (Facebook, Instagram, X, TikTok, LINE, Threads) and 4 snippets; migration `FacebookOnlyBumpPlans` deleted the sample accounts of existing workspaces (every account of another platform, and every account without a device whose name is not `Facebook · <browser>`; their posts cascade; link sets drop their ids). Facebook groups and pages are the ONLY thing the system posts to: `Platform` has the single value `fb` (the API still says `"fb"`), `PlatformLimits` is `{ fb }` (old stored workspaces may hold the other keys: ignored), and the extension never knew other networks. LINE as a NOTIFICATION channel (Telegram + LINE OA messages) is a different feature and stays. Tests that need "an account without a browser" make one with `SeedAccountAsync` (`WorkflowTestSupport`).
- Devices (`Features/Devices`). The owner creates a pairing code (`DevicePairing`, 10 minutes, single use, day-old codes are deleted whenever a new one is made; the number of devices comes from the owner's plan, `PlanSetting.Devices`: free/basic 1, pro 3, agency unlimited by default). The extension trades it at `POST /api/device/pair` for a device key (only its SHA-256 is stored) and the workspace gets a connected Facebook account (`SocialAccount.DeviceId`). Device endpoints authenticate with the `X-Device-Key` header (`DeviceKeyAuthenticationHandler`, scheme `DeviceKey`, open CORS policy `Devices`) and read the caller from `ICurrentDevice`. The web app controls a device with `PUT /api/workspaces/{ws}/devices/{id}` (`UpdateDeviceCommand`, admin role): `name` (its account follows: `SocialAccount.FollowDevice`; names are UNIQUE inside a workspace, compared without regard to case: renaming to a taken name is a 422 "มีส่วนขยายชื่อ ... อยู่ในบัญชีนี้แล้ว", and a browser that pairs with a taken name gets "name (2)", "(3)"... through `Device.UniqueName`; unique index (workspace, name), and the migration renamed existing duplicates) and `jobsPaused` (`Device.JobsPaused`: `ClaimJobCommandHandler` hands out nothing, the heartbeat reports it); null keeps a value. Unbinding (the owner's `DELETE` and the admin's) goes through `DeviceRevocation`: it fails the device's claimed and still-open posts, so nothing stays `Posting` or queued for a browser that is gone. The heartbeat's `jobsPaused` is true when the device is paused **or** the owner cannot post (`!CanPost`), so the extension stops asking.
- Jobs. The extension sends `PUT /api/device/groups` (name + URL; they become the account's `Groups`/`GroupLinks`, names unique) and polls `POST /api/device/jobs/claim`. A job (`JobDto`) has `kind` (`post`, or `bump`: see "Bumping"), `targetKind` (`group`|`page`: a page needs the browser to act as the page first) and `pageTags` (the schedule's collection's page tags, always a string: an empty one tags nobody; the extension has no shop page of its own any more). `ClaimJobCommandHandler` hands out one due post at a time per device, keeps the anti-ban minimum gap per account, fails posts over the platform's 24-hour limit (`quota`; `AntiBan.Limits`, 1–500 per platform, `AntiBanSettings.MaxDailyLimit`, counted per workspace and platform, so a schedule of 216 Facebook posts a day needs the Facebook limit at 216 or more) or for a group the extension no longer has, skips posts later than `OfflineSettings.MaxLateness`, and fails claims not reported within 15 minutes (never retried automatically: they may have gone out). `POST /api/device/jobs/{id}/result` completes it (`needsLogin` → `session` + account `relogin`, `blocked` → `rate_limit`). Claiming writes a `post` event. `OfflineSettings.MaxLateness` counts from the later of the due time and the end of the anti-ban gap, so a post held back by pacing is not "late" (two posts due together would otherwise leave the second one skipped). `PUT /api/device/groups` accepts up to `MaxGroups` (5,000) groups, a repeated name is dropped (the extension makes names unique itself and keeps the name the web already has for an address, because queued posts name their group), and it writes `device.groups` only when the list changed. Connected accounts without groups cannot be scheduled for.
- Posting workflow (the web app's three steps; `Features/Collections`, `Features/LinkSets`, `Features/Schedules`, `DTOs/WorkflowDtos.cs`). **Collections** (`PostCollection` + owned jsonb `CollectionSettings`: hashtags, page tags, footer + position, shuffle, watermark + position, `RequireApproval`) hold **`CollectionPost`s** (master posts, see "Post library": text ≤5,000, media ids from the library, `Approval` draft → pending → approved; changing the `RequireApproval` switch itself needs an admin (an editor's save that keeps it stays editor-level; 403 otherwise); with `RequireApproval` a new or edited post starts as draft, `request` needs an editor, `approve`/`reject` an admin, only approved posts are used; ≤5,000 posts per workspace, 100 collections). **Link sets** (`LinkSet`: name, `PostAsAccountId` = the connected Facebook account whose browser posts, null = the first connected one (`LinkSetAccounts.PostingAccount`), `AccountIds` = other accounts that post the same text to their `DefaultTarget`) hold **`SetLink`s** (NOT the `GroupLink` value class of `SocialAccount`): name, URL, group code, `DailyMax` (0–50, 0 = unlimited), `Enabled`, `Health` (ok / pending = last post awaits group approval / off), `FailStreak`; ≤200 links per set, 100 sets. The URL is normalised (`FacebookGroupUrl.Normalize`) to `https://www.facebook.com/groups/<slug>` for a GROUP or, for a Facebook PAGE, to its vanity address (`facebook.com/<name>`, 5+ letters/digits/dots with a letter, not a reserved segment such as watch/marketplace/login/groups), `profile.php?id=<id>`, `/pages/<name>/<id>` or `/p/<name-id>`; `SetLinkDto.Kind` is `group` or `page` (from the address, no column), anything else is stored raw and `Valid` is false (never used, shown red). The same rules are mirrored by `facebookTarget()` in `client/lib/shared.js` and `core/flow/group-links.ts` in the UI: keep the three in step; `Duplicate` is computed per set (group addresses are compared without regard to case everywhere: `FacebookGroupUrl.Same`/`Comparer` decide for the flag, the schedule's targets, bulk paste, CSV import, import from a browser and a restore's address keys; a link keeps its slug as typed, and a slug without a letter or digit is not a group, so it is stored raw and invalid). Bulk paste (`url | code` lines), CSV import (`set,name,url,code`), import from a connected account's synced groups (`GET accounts/{id}/groups`) and "enable again" are endpoints; a link set or collection that a schedule uses cannot be deleted (422 naming the schedules, and the FKs are NO ACTION). Nothing here is seeded into new workspaces: a demo schedule would post to real groups once a device is paired.
- Library clean-up tool (`tools/post-cleanup/`, Python, see its README.md; 2026-10-05). `cleanup_posts.py` reads one workspace's `COLLECTION_POSTS` and decides per post by rules (`plan.py`: 2026 ad copy kept after `clean26.py`, curated evergreen posts, reusable sentences of old posts rebuilt by `build_old.py`, SEO walls / shop notices / thank-yous / near-duplicates switched off with a reason); a kept post is rewritten as `{{code}}` + the 5-line promo block + body + 6 hashtags, every post gets the poster and the promo video as its first two media (20 files at most), the collection's `PageTags` is set. Writes only with `--commit`; a dry run rolls back. It needs the post-MasterPosts schema (`active` column). `r2.py` is a minimal SigV4 client for the media bucket.
- Videos for Facebook (2026-10-06, `Domain/Services/Mp4Layout`, `MediaResponse.ToDeviceResultAsync`). An MP4 whose index (`moov`) sits after the picture data (`mdat`) or that carries a big cover picture in `udta` (ffmpeg remux with an attached poster; the shop's SIRI_Promo_Voice.mp4 was exactly that) plays everywhere but never finishes processing in Facebook's post composer (checked on a real logged-in composer: spinner and blank thumbnails; the same bytes with the index first went through). `GET /api/device/media/{id}` therefore sends every `video/mp4|quicktime|x-m4v` through `Mp4Layout.ForFacebook`: lossless (sample bytes identical, chunk offsets `stco`/`co64` moved, a `udta` over 64 KB dropped, order `ftyp, moov, rest`), returns null (file sent as stored) for fragmented, damaged, non-MP4 or already-fine files, never throws. The library file and the R2 object are NOT changed (the web library still plays the original), so any source of a video is covered: web upload, import, R2 put by a tool. It reads the file into memory for that (library files are 100 MB at most). Tests: `Mp4LayoutTests` (Domain) and `A_video_whose_index_is_at_the_end_reaches_the_device_with_the_index_first` (integration). It cannot fix a video Facebook rejects for its codec (HEVC, VP9, unusual profiles): there is no transcoder here.
- Post library / master posts (`Features/MasterPosts`, `MasterPostsController` at `master-posts`, `Domain/Entities/CollectionPost.cs`). Since migration `MasterPosts` a `CollectionPost` is a **master post** of the workspace, not a child of one collection: it sits in any number of collections through `CollectionMember` (table `COLLECTION_MEMBERS`, key = collection + post, cascades on both sides; ≤50 collections per post, ≤5,000 posts per workspace) or in none (it waits in the library). The migration copied every old post's `collection_id` into a membership first. A post manages itself: `Active` (off = `IsUsable` is false in every collection, no schedule draws it, its queued future posts are removed; on = the schedules fill in what is missing), `Approval` (global per post: a collection with `RequireApproval` only uses approved ones; a text/media change sends an approved post back to draft when ANY of its collections requires approval; adding it to such a collection does not reset it) and `CollectionPostSettings` (jsonb `settings`, `HasJsonConversion`): own `Hashtags`/`Footer`/`FooterPos` (null = follow the collection, "" = none; `CollectionPost.SettingsIn(collection)` is what `PostComposer` gets, also for the test post), and own timing limits the materializer checks on top of the schedule's times: `ValidFrom`/`ValidUntil` (local days), `Weekdays` (0 = Sunday), `TimeFrom`/`TimeTo` (window, may wrap midnight), `MaxPerDay` (0–50 uses per local day over all groups; counted from this run plus `IPostRepository.ListScheduledAtByCollectionPostAsync`, queried only when some usable post has a limit). In `ScheduleMaterializer` a slot a post does not allow does not get it: rotate takes the next post in turn that allows the slot (the cursor moves past the ones that did not), shuffle draws among the allowing ones (and falls back to one the group had lately rather than leave the slot empty); a slot nobody allows makes nothing but still counts as generated. `ICollectionPostRepository.ListByCollectionAsync` still means "the posts of this collection" (a join through the members), so engine code did not change shape. Collection endpoints keep working: `POST collections/{id}/posts` writes a new master post straight into it, `POST collections/{id}/posts/add` puts existing ones in, `DELETE collections/{id}/posts/{postId}` only takes the post OUT of the collection (the library keeps it; `DELETE master-posts/{id}` deletes for good), a collection delete leaves its posts in the library. `CollectionPostSync.ChangedAsync` is what every post change calls: it removes the queued future posts the post made for the schedules of the affected collections (text, media, settings, switch, collection or delete changes) and invalidates `GeneratedThrough` so `SourceTopUp` refills them; slots that are still full are not touched, so a post switched back on is used from the slots made later. `CollectionPostDto` has no `collectionId` any more: `collectionIds`, `active`, `settings` and the counters (`postedCount`, `queuedCount`, `failedCount`, `lastPostedAt`, `nextAt`, from `IPostRepository.UsageByCollectionPostAsync`; tests excluded) instead; `GET master-posts/{id}/activity` lists the newest posts it made; `POST master-posts/bulk` (≤500 ids) activates, deactivates, deletes and adds to/removes from a collection. The backup keeps posts inside their collections with `active`/`settings` and a `key` shared by the copies of a post that sits in several collections, plus a top-level `posts` list for the ones in no collection; a file from before the library (no key) restores each post as its own.
- Composing (`Domain/Services/PostComposer`, mirrored by `src/app/core/flow/compose.ts` in the UI: keep both in step). `{a|b}` spintax is resolved innermost first, `{{code}}` / `{{รหัส}}` is replaced by the group code, otherwise the code becomes the first line; the footer (top or end) and the hashtags are added unless the text already contains them; composed text longer than `Post.MaxComposedLength` (7,000: a 5,000-character post plus group code, footer and hashtags must fit; `POSTS.content` is that wide) is refused, never cut (but a spintax pick that is too long is spun again, up to 30 picks, before the shortest one is refused; the UI preview does not enforce the limit). A `{{code}}` that sits alone on its line leaves no blank line when the group has no code (`PostComposer.Compose`, `compose.ts`), so a post may start with `{{code}}` and put a block (the shop's promo) under the group code. Page tags, watermark and "shuffle image order" are stored only: nothing applies them yet.
- Schedules (`Schedule`, `ScheduleMaterializer`, `ScheduleTopUp`, `Application/Common/ScheduleEngine.cs`). A schedule pairs one collection with one link set: mode daily / weekdays / weekend (**Fri–Sun**, the design's label) / interval (rounds every N hours from a first time) / drip (N posts spread between two times) / once (a date + time), start date, post order (shuffle: every group gets ONE post per slot, picked at random from a deck without replacement shared by the groups of the slot, so groups of one round get different posts; rotate: one post per slot for everyone, `Cursor` persisted) and, for shuffle, `Schedule.Repeat` (`PostRepeat`, migration `SchedulePostRepeat`): `recent` (default: not the link's last post, and not one of its last `RecentAvoid` posts), `any` (a group may get the same post again, even within a day; the database is not asked for history) or `never` (a link never gets a post it ever had, queued or sent, until it has had every post of the collection, then it starts over keeping away from its last ones; `IPostRepository.ListAllCollectionPostIdsByLinkAsync`); account targets without a link only remember what this run gave them, per-target time overrides (keys = link id in N format or `account:<id>`), `BumpHours` + `Bump` (the bump plan, see "Bumping") and `AutoDeleteDays` (**stored only**: the extension cannot delete posts yet). It materialises ordinary `Post` rows (status queued, `ScheduleId`, `CollectionPostId`, `LinkId`, `TargetKey` `link:<id>`/`account:<id>`, `SlotKey`, `TargetUrl`, `Code`, composed `Content`) 14 local days ahead in the schedule's calendar (`UtcOffsetMinutes` comes from the browser); targets of one slot follow each other `AntiBan.Min..Max` minutes apart (a random gap each time, the first target at the slot, and in a random order when `AntiBan.Shuffle` ("shuffle the order of target groups") is on, so the groups go out one by one like a person moving through Facebook), past slots are skipped, and a unique partial index on (schedule, target, slot) makes a run idempotent (the loser of a race discards and retries). `ScheduleTopUp.EnsureAsync` runs first in every claim (one query when nothing is due) and extends active schedules; pausing deletes every post of the schedule that still waits for a browser (queued, due or not, and held; never one being posted or finished), resuming regenerates, deleting does both; a `once` schedule switches itself off after its day; `GeneratedThrough` does not advance while nothing could be generated (no usable post, no connected browser), so a later top-up fills the gap. Guards: **start choice**: `SaveScheduleRequest.StartNow` (`Schedule.StartNow`/`NowPending`; false = wait for the times) queues one opening round the moment the schedule is created (slot `<today>Tnow`, every target once, the first 2–20 s from now, the rest spaced like any slot) before the regular times; the start date is forced to today, a Once schedule ignores its time and is only that round, `NowPending` is cleared by the run that queues it so pausing and resuming never repeats it (and it stays set while nothing can be posted, e.g. no group), and backups do not carry it; a start date between yesterday and 366 days ahead in the schedule's calendar (`Schedule.StartDateRange`: the validator answers 400, `Schedule.Create` 422, a restore refuses a later date and moves an older one up to yesterday), at most 10,000 queued posts still to come per workspace (`QueueFullException`, 422: creating, resuming and restoring run in a transaction under a per-workspace lock so a refusal leaves nothing behind; the background top-up logs it and leaves the schedule alone for ten minutes), 50 schedules per workspace, 2,000 posts per run (`Schedule.MaxPostsPerRun`, counted in whole days: a big schedule such as 72 groups × 3 times = 216 a day gets the days that fit, `GeneratedThrough` stops at the last whole day and the next top-up, i.e. the next claim, makes the rest; only ONE day of more than 2,000 is refused, `ScheduleMaterializer.TooManyPerDay`), ≥1 usable post, ≥1 usable target and a connected Facebook account at creation (422 with a Thai reason). `GET schedules/best-times` = the three hours with the most successful posts in 30 days.
- Bumping (2026-10-06; a PREMIUM feature, `User.HasBump` = the `bump` entry of `PlanFeatures` = the top plan `agency`, shown as "Premium"). `Schedule.BumpHours` (0, 1, 2, 3, 6, 12, 24; 0 = off) and `Schedule.Bump` (`BumpPlan`, jsonb column `bump_plan`: `Rounds` 1-3, `Text` (spintax; blank = `BumpPlan.DefaultText`), `MediaIds` (library files to draw from, <= 20) and `ImagesEach` 0-5). Creating a schedule with `BumpHours > 0` is a 403 (`FeatureGates.PremiumRequired`) for an owner without the feature. The extension reports where a post went up on Facebook (`ResultRequest.PostUrl`, read from the feed by `content.js` `findNewPostUrl`, matched by the first characters of the text; `Post.PostUrl`, only Facebook addresses are kept). When a schedule post is reported as posted (not awaiting approval, not a test) with an address, for an owner with the feature, `BumpPlanner.Plan` makes `PostBump` rows (table `POST_BUMPS`, one per post and round, unique): the first `BumpHours` after `PublishedAt`, each next one that long after the one before, a few minutes of jitter, its own spun text and its own random images. A bump is NOT a `Post`: it is not in the calendar, reports, errors or the day's counts. `POST /api/device/jobs/claim` hands out due posts first and, when none is due, the due bump of the device's account (`JobDto.Kind = "bump"`, `GroupUrl` = the post's address, `PostId` = the bump id); one job at a time per device (a claimed bump not reported within 15 minutes fails, never retried), the anti-ban pause counts the last post OR bump, a bump more than 12 hours overdue or whose schedule is gone is skipped, nothing is handed out when the owner no longer has the feature (a downgrade). The result goes to `POST /api/device/bumps/{id}/result` (`ok`, `needsLogin` -> account `relogin`, `blocked` -> the device rests like after a blocked post). Unbinding a device skips its open bumps. The backup keeps the bump plan. Extension side: `runCloudBump` / `commentOnPost` in `background.js` (open the post, a human-like pause, `openCommentBox`, type or paste the text, attach the images, wait for the upload, `submitComment`, check the box emptied) with `content.js` handlers `openCommentBox`, `commentState`, `submitComment`; a comment box picked by `openCommentBox` becomes the target of the generic editing commands (`findComposer` falls back to it). `client/tools/test-bump-flow.mjs` covers it (needs `TEST_PSQL` to move the due time) and `ExtensionsAndPackagesTests` covers the API with the test clock.
- Packages (`PlanSetting`, `PlanFeatures`, `PlanQuotas`; 2026-10-06). Besides accounts, posts per 24 hours, devices and seats, a plan now limits GROUPS (links of the link sets, `Groups`), IMAGES (files of the media library) and LIBRARY POSTS (master posts), each counted over all of the owner's workspaces; null = unlimited. Defaults: Free 1/10/1/1 + 10 groups, 20 images, 20 posts; Basic 2/50/1/1 + 50/200/200; Pro 10/300/3/3 + 300/1000/1000; Agency ("Premium") unlimited but 10 seats. The admin edits the numbers (plan settings, per-customer overrides `LimitOverrides`: null keeps, 0 = unlimited); which FEATURES each plan includes is code (`PlanFeatures.For`): Pro = `advanced_anti_ban`, `notifications`, `auto_reply`, `ai`; Agency = those + `bump` + `client_reports`; Free/Basic none. `PlanDto.Features`, `WorkspaceDto.Ai/Bump` (+ the older flags) carry them to the web app. `PlanQuotas` (scoped service) refuses with a 422 naming the limit and the use: adding links (`AddLink`, bulk, CSV, import from an account), uploading media, adding library posts (`AddCollectionPost(s)`, `CreateMasterPost`), and a backup restore (`EnsureRestoreFitsAsync`: the file plus the owner's OTHER workspaces). `BillingDto.Usage` has the same three counts. Existing data over a new limit stays: only adding is refused.
- AI post drafts (`Features/Ai`, `AiController`, `Infrastructure/Ai/AnthropicAiWriter`; 2026-10-06). The PLATFORM holds one key (`Ai__ApiKey`, `Ai__Model` default `claude-sonnet-5-5`, `Ai__DailyLimit` drafts per workspace per UTC day, default 50, 0 = none; `deploy/prepare-env.sh` passes `Ai__*` into the pod); the key never reaches the browser. `GET /api/workspaces/{ws}/ai/status` -> `{ enabled (a key is set), allowed (the owner's plan has `ai`), model, draftsLeftToday }`, `POST .../ai/posts` `{ topic, points[<=10], tone friendly|formal|sales|short, count 1-5 }` -> `{ variants[] }` (editor role; 403 plan, 422 no key / allowance used / provider failed, 400 input). Drafts are NEVER saved by the API: the web app puts them in the post editor. The system prompt asks for Thai Facebook-group posts with `{{code}}` on the first line and `{a|b}` spintax and JSON `{"variants":[...]}` (parsed tolerantly, a code fence is fine); the workspace's text goes in the user turn only. The per-day count (`AiUsage`) is in memory (a restart gives a fresh day: a cost guard, not a ledger). The integration tests replace the writer with `FakeAiWriter`.
- Concurrency of the engine. `IUnitOfWork.ExecuteInTransactionAsync(lockName, work)` runs work in one transaction after `pg_advisory_xact_lock` on the name (`lock_timeout` 20 s; a nested call joins the outer one; device events are published after the outermost commit). `ScheduleTopUp.GenerateAsync` takes one lock per schedule and reads again after it, so claims arriving together fill a gap once instead of deadlocking on the unique slot index. `AppDbContext` maps deadlock (40P01), serialization failure (40001), lock timeout (55P03) and `DbUpdateConcurrencyException` to `ConcurrencyConflictException` (409); generation retries up to 3 times and then gives up quietly. `Post` carries the `xmin` concurrency token (a claim that loses the race gets nothing). `ScheduleTopUp.EnsureAsync` never throws into a claim (cancellation excepted): a failure is logged with the schedule id and the schedule is left alone for 10 minutes (`TopUpThrottle`, in-process singleton; creating, resuming and restoring bypass it).
- Edits reach queued posts (`Application/Common/ScheduleSync`). A schedule queues a fortnight ahead, so deleting a link, switching it off, or changing its address or code removes that link's queued future posts (`IPostRepository.ListFutureQueuedByLinkAsync`), changing the set's posting account or removing an account removes the schedules' queued future posts, and every such change (and a link added, switched on, imported or pasted) clears `Schedule.GeneratedThrough` (`InvalidateGenerated`) so the next claim's top-up makes what is missing; slots that are still there are kept by the unique (schedule, target, slot) index, so nothing is queued twice. Posts a device has taken or that went out are never touched, and posts due now are left to the claim, which already skips a group that is off or gone.
- Claim and result rules for workflow posts (`Features/Devices/Devices.cs`). The URL is `TargetUrl ?? account.UrlFor(Target)` (legacy posts keep working). The legacy server has no unit test project. Its only automated test is `test-online.mjs`, which needs a live server and database. `test-cloud.mjs` fakes the Facebook page too (content commands in `tools/cloud-harness.mjs`, shared with `test-schedule-flow.mjs`), so it posts end to end without a browser. ## Legacy backend configuration quirks

- `Program.cs` reads a `.env` file from the current directory or its parent before startup. Variables already set in the environment win.
- Connection string: `ConnectionStrings:Default`, falling back to `AppSettings:ConnectionStrings`. Its database name is then **replaced** by `Database:Name`: `SIRIAUTOPOST` in Development and `SIRIAUTOPOST_PRD` otherwise, Docker included. The server creates the database on first start, so the DB user needs CREATEDB.
- The database is shared with other apps. Every table is prefixed `FBAP_` and upper case (`FBAP_PROFILES`, migration `UppercaseTableNames`; raw SQL quotes the names), the migrations history table is `fbap_ef_migrations` (lower case on purpose: renaming it would re-run `Initial` on existing databases), and columns are snake_case (`UseSnakeCaseNamingConvention`). Changing a table name needs a migration **and** the quoted SQL in `ProfileStore`, `AdminEndpoints` and `DeviceEndpoints`; CI starts the server, so a mismatch fails there.
- The first start seeds an admin from `Admin:Username`/`Admin:Password`. If no password is set, it generates one and logs it.
- Use the **root** `docker-compose.yml` (the old `backend/docker-compose.yml` is gone).
- The `<None Include="..\..\dashboard.html" ...>` items in the csproj resolve to the repo root, not `client/`, so a plain `dotnet publish` doesn't copy the extension files. The Dockerfile copies them into `/out/extension` itself.

## Legacy architecture

### Three API surfaces (`backend/SIRI.AUTOPOST.Server/Endpoints/`)

- `AuthEndpoints`: `/api/auth/*`, cookie auth (`fbap.auth`). Unauthenticated `/api` calls get a 401; page requests are redirected to `/login.html`.
- `AdminEndpoints`: `/api/*` (requires login). Covers profiles (configs), profile images, devices, live device state and logs, and remote commands.
- `DeviceEndpoints`: `/api/device/*`, used by the extension's service worker. It authenticates with the `X-Device-Key` header (only its SHA-256 hash is stored) and has an open CORS policy. `POST /heartbeat` uploads state and logs, and returns the config revision and any pending commands.

### Domain model (`Data/AppDb.cs`)

- **Profile**: one extension "settings" JSON blob (version 2 shape: `campaigns`, groups, posts, global settings, Telegram), stored as `jsonb`, with a `Revision` counter. Several devices can share one profile.
- **ProfileImage**: media stored as bytes, keyed `(ProfileId, ImageId)`. The ID matches the extension's `img:<id>` storage key. An image ID never changes content, so existing IDs are never overwritten.
- **Device**: one computer running the extension, with its last reported `State` (jsonb). It counts as online if seen within the last 100s (`AdminEndpoints.OnlineWindow`).
- **DeviceCommand**: a queued remote command (pending → sent → done/expired). Commands older than 10 minutes expire instead of running late.

### Settings sync (`Services/ProfileStore.cs` + `client/background.js` "online" section)

- `SaveSettings` uses optimistic concurrency. The caller sends `baseRevision`; if the row has moved on, the API returns 409, and `null` overwrites. Saving identical JSON keeps the revision so devices don't reload for nothing.
- After each save, images that no settings reference and that are older than 1 hour are deleted. The grace period exists because editors upload images before saving the settings that use them.
- The extension syncs every 30s through a `chrome.alarms` entry (`fbap-sync`). It pulls when the revision changes, fetches only missing images, and pushes local edits after about 4s. When both sides changed, the server wins.
- `Services/Helpers.cs` `SettingsJson` reads the extension's JSON on the server side. It mirrors `migrateSettings`/`campaignImageIds` in `client/lib/shared.js` and `hasContent` in `client/lib/backup.js`. If the settings shape changes, update both sides.

### The web editor reuses the extension's dashboard

The server serves `client/dashboard.{html,css,js}`, `lib/*.js` and `icons/` under `/app/`, located at runtime by `ExtensionPath()`. `GET /app/dashboard.html` injects `wwwroot/web/shim.js` before `dashboard.js`. The shim replaces `chrome.storage.local`, `chrome.runtime.sendMessage` and `chrome.permissions` with REST calls:

- `settings` and `img:*` storage keys map to profile endpoints (`?profile=<id>`).
- `sendMessage` commands become `DeviceCommand`s for the selected device (`?device=<id>`). The shim polls until the command is done.

So `dashboard.js` must keep talking only through those chrome APIs. A new chrome API used there needs a shim implementation too. `wwwroot/index.html` + `web/admin.js` hold the profile and device management page.

### Extension internals (`client/`)

- `background.js` (service worker): every campaign has its own `chrome.alarms` entry (`fbap:<campaignId>`). Ticks are serialized through one promise chain, so only one post happens at a time across all campaigns, in a dedicated worker window. It also handles anti-block rules (daily quotas, group cooldowns, auto-pause on Facebook warnings), Telegram notifications, the bundled-config loader, and server sync.
- `content.js` is injected with `chrome.scripting.executeScript` into the Facebook tab. It does the DOM steps (scroll, type, attach, click post).
- Messaging is `{ target: 'fbap-bg' | 'fbap-content', cmd, ...args }` → `{ ok, ... }`. The dashboard calls background commands, and background calls content handlers.
- Remote commands: the names in `AdminEndpoints.AllowedCommands` must match `remoteCommands` in `background.js`, and the shim's `LOCAL_ONLY` list blocks commands the web can't run.
- `lib/shared.js` holds settings defaults, `migrateSettings`, spintax and the text composer. `lib/backup.js` handles import/export and the bundled `config/autopost-config.json`, which loads automatically only when the browser profile has no data. `lib/siri-import.js` + `lib/zip.js` import SIRI exports.
- The files under `client/config/` (`extra-groups.txt`, `drop-images.txt`, `image-fixes/`) are only inputs for `tools/siri-to-config.mjs`. The extension never reads them at runtime.
- Cloud mode (`background.js` "cloud" section, shown on `status.html`): pairs with `SIRIAUTOPOST.Api` (storage key `cloud`), and every 30 s (`fbap-cloud` alarm, run through `enqueue` so it never overlaps a campaign post) sends a heartbeat and the enabled groups of every campaign, claims one job and posts it with `postToGroup`. Job media is stored as `cloudimg:<id>` (content.js `loadFiles` accepts full keys) and removed after the post, so the `img:` orphan cleanups never touch it. It is independent of Start/Stop and of the legacy online mode; the shim's `LOCAL_ONLY` keeps the `cloud*` commands out of the web editor. The same alarm also runs `cloudConfigSync` **outside** `enqueue` (so a "stop" from the web arrives during a post): it reports state and log, syncs the settings with `ExtensionConfig` by the legacy rules (first sync with an empty web config uploads this browser's settings, then the changed side wins, the web wins when both changed; `cloud.configRevision`/`configHash` find local edits, `cloudPulled` makes the dashboard reload), then runs the web's commands through `runRemoteCommands`. Local edits push about 4 s after the change (`scheduleCloudPush`). Between alarms, `cloudListen()` (started by `ensureCloudAlarm` and the alarm) loops on `cloudConfigSync({ wait: true })`: the server holds `/api/device/sync` open until the web sends a command, so buttons arrive within a second; `cloudWake()` aborts the held call (`cloudApi` takes a `signal`, the answer is `{ aborted: true }`) whenever a plain sync is requested, so an edit or the alarm is never stuck behind it, and a 20 s `getPlatformInfo` tick keeps the worker alive while a call is open. `cloud.paused` mirrors the web's `jobsPaused`. A schedule of the web's posting flow needs nothing in the extension's own campaigns: a job carries its group address and text (`TargetUrl`, `Content`), so the extension posts with its settings empty, except the page tag: `runCloudJob` gives `postToGroup` `job.pageTags` when the server sends it, else `DEFAULT_CONFIG.pageTags` (the shop's Facebook page), so the first place the text names that page (the promo block) is typed as a clickable `@mention` (`typeTag`; plain text when Facebook does not suggest the page). The web's `takeJobs` command (`remoteCommands`, also in `DeviceCommand.Allowed` and a `StartsPosting` command) runs `cloudTick` in the post queue at once instead of at the next 30 s round. A 401 from the API (unbound on the web) resets `cloud` to "not paired" (`cloudForget`); the campaigns stay. `test-cloud.mjs` covers it.
- Pairing starts on the web: "Connect this Chrome" opens `<web origin>/connect-extension#ap-pair=1&code=...&name=...&ws=...`; `chrome.tabs.onUpdated` (`connectRequest`) sends that tab to `status.html#pair=...`, where one "Allow" click requests the optional `<all_urls>` capture permission (Chrome grants it only on a click in the extension) and runs `cloudPair`. The API URL is always the origin of that page. There is no manual code entry. The page may be open in a Chrome that is not signed in to the web app at all (another computer or profile) or signed in as another person, so after a successful pairing `status.js` shows ONLY "เชื่อมต่อสำเร็จ" with a close-tab button (no redirect to the web app, no workspace details) until the page is opened again. A workspace may have many extensions (each paired browser is a `Device` + its Facebook account); a link set's `PostAsAccountId` and the test page's extension select decide which one posts. Version 2.3.0 adds bumping, page posting (`switchProfile`: when Facebook offers "Switch now" on a page you manage, the extension acts as the page and reloads), the anti-ban settings from the job (`typingSpeed`, focus window, rest after a block), and `facebookTarget()` in `lib/shared.js` (group or page addresses).
- `dashboard.html/js` is retired inside the extension (it redirects to `status.html` on `chrome-extension:`); it stays only as the legacy server's web editor. The legacy online mode still runs in `background.js` for browsers already connected, but has no UI any more.

## Duplicated files

`siri_autopost_ui/legacy/` contains byte-identical copies of `client/dashboard.{css,js}`, `client/lib/*` and `client/icons/`, and near-copies of `client/dashboard.html` and `backend/SIRI.AUTOPOST.Server/wwwroot/{index,login}.html` + `web/*`. The near-copies drop the `/app/` path prefix and load the shim as a module. `siri_autopost_ui/src/app/core/ext/lib/` holds byte-identical copies of `client/lib/{shared,backup,zip,siri-import}.js` (with hand-written `.d.ts` files) for the Angular campaigns screen. When you change any of these files, mirror the change in the other repo. Library code shared with browser bundles must not import Node modules by a literal specifier (see the `node:zlib`/`node:crypto` fallbacks in `zip.js`/`siri-import.js`).
